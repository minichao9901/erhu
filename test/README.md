# 二胡调音器 · 测试

零依赖，纯 Node 运行（Node 18+ 即可），**不需要 npm install**。

```bash
node test/run-all.js     # 一次跑完两套（共 291 项）
node test/dsp.test.js    # 125 项：YIN 算法 + 乐理 / 音位模型
node test/ui.test.js     # 166 项：整页交互（DOM 与 AudioContext 桩，无需浏览器）
```

两套测试都**直接从 `../index.html` 里抽取被测代码**运行，所以改完页面直接重跑即可，
不存在"测试和实现不同步"的问题，也不需要构建步骤。

## dsp.test.js —— 算法与乐理

| 覆盖 | 说明 |
|---|---|
| YIN 基频精度 | 纯音误差 <0.1 音分；高把位 1568Hz 处 <0.5 音分 |
| 二胡音色 | 4 种音色（含基频弱于二次谐波）都不出现八度误判 |
| 噪声与静音 | 白噪声正确拒绝，19dB 信噪比下误差 1.5 音分内 |
| **六个调的弦式** | 1=D/G/F/C/A/bB → 15/52/63/26/41/37 弦 |
| **简谱八度点** | 中音区锚定中央 C，1=G 时内弦 D4 是带下加点的 5̣ |
| **半音间距模型** | 逐调锁定两弦完整半音序列；解释两弦指距为何不同 |
| 把位跨度 | 1=D 时三个把位都是纯五度（7 个半音） |

**为什么要锁这些**：把位、弦式、八度点是专业领域知识，错一个数字拉琴的人一眼就能看出来。
测试里逐个调写死了期望值，任何改动导致音位错位都会立刻失败。

**容易搞错的一处**：大调音阶从主音往上数 6 级是**大七度**（11 个半音），
从属音往上数 6 级是**小七度**（10 个半音）。所以两根弦同一音位的真实指距不同，
面板必须各算各的——共用纵坐标会把外弦的「3̇→4̇ 半音」画成全音。

## ui.test.js —— 整页交互

用 DOM 桩 + AudioContext 桩 + **假定时器**跑完整交互链路，不需要浏览器和麦克风。
假定时器让"每秒一步"的音阶和节拍器能瞬间跑完，测起来是毫秒级。

| 覆盖 | 说明 |
|---|---|
| 完整链路 | 点「开始调音」→ 授权 → 渲染 → 读数 |
| 箭头落点 | 像素级校验（-30 音分实测偏移 21.0px，理论 21.0px） |
| 判绿门槛 | ±4 音分判绿、+9 不判绿 |
| 点击音位发声 | 基频与 2/3/4 次谐波、琥珀高亮、再点停止 |
| 音阶练习 | 首音 D4、逐音前进、到顶折返、到底折返、随调变化 |
| 节拍器 | 9 档速度、BPM↔毫秒换算、120BPM 拍数是 60BPM 的两倍 |
| 错误分支 | 非 HTTPS、权限拒绝、微信内核、无 getUserMedia、麦克风被占用 |

### 三条音频防回归（都来自真机踩坑）

1. **`interrupted` 状态**：iOS 从后台切回来时 `AudioContext` 会变成 `interrupted`
   而不是 `suspended`，只判 `suspended` 会导致"第一次响、再打开不响"。
2. **双定时器乱节奏**：切换音阶拍数时若只覆盖 `scaleTimer` 变量而没 `clearTimeout`，
   旧定时器会残留并发，节奏成倍乱跳。测试断言"切换后只走 2 步"（旧代码会走 3 步以上）。
3. **静音拨片**：音频起不来时必须在 350ms 后主动提示，不能让用户对着没声音的按钮干等。

## 加测试的建议

- **领域数据优先**：音位、弦式、半音序列这类"错了就是错"的值，写死期望值逐个校验
- **写能复现真实 bug 的断言**：上面第 2 条就是照着一个真机报告写的回归测试
- **断言要能区分新旧实现**：如果一条断言在改坏代码后依然通过，它就没有价值

## rig/ —— 真机问题复现台

用户报"拉琴时不灵敏/跟不上"时，用这套工具在本地复现，不靠猜。

### 1) 喇叭→麦克风（测声学路径 + 完整链路）

```bash
node test/rig/gen-wav.js wav/     # 生成二胡仿真音频（纯音/强谐波/弱基频/揉弦/轻奏/噪声）
node test/rig/measure.js          # 起本地服务 + 真实浏览器 + 真实麦克风
                                  # 自动点「开始调音」(CDP 可信手势) → 播放 → 读检出统计
```

会打印每个用例的：检出率 / 门限挡 / 认不出 / 可信度不足 / 帧间不稳 / 平均 dBFS。
**注意**：房间噪声与系统音量会波动，同一用例不同轮次可能差 20 个百分点，
只看方向性结论，别拿来精调参数。

### 2) 直接解码真实录音（推荐，精确且可重复）

```bash
ffmpeg -i 曲目.mp4 -vn -ac 1 -ar 48000 -c:a pcm_f32le seg.wav
node test/rig/analyze-song.js seg.wav [起始秒] [时长秒]
node test/rig/sweep-config.js seg.wav     # 参数扫描，比不同配置的检出率
```

`analyze-song.js` **从 index.html 里读取参数**，所以永远和线上一致；
输出逐帧统计、失败分项、转谱（含每个音的平均音分），并写成 `*-notes.txt`。

用它测真实演奏《翻身歌》得到的结论：
- 现状（窗4096/平滑5帧/中位数判稳）：61s 快板段检出率仅 26%，误杀 935 帧
- 改为「平滑3帧 + 自适应判稳（可信度≥0.8 立即响应）」：同段 82%，误杀降到 34 帧
- 长音音分误差 ±5 以内（准）；2 帧（80ms）的超短音因平滑窗口不够而不可信，
  这是物理限制：4096 窗=85ms，比它更短的音符必然被相邻音污染

### 3) 简谱 JSON → 音频（生成练习伴奏）

```bash
node test/rig/render-jianpu.js 简谱.json 输出.wav [--bb-first6|--no-bb-shift]
node test/rig/verify-render.js 输出.wav [--bb-first6|--no-bb-shift]   # 回环验证
```

读简谱 JSON（含 `measures[].notes[].{degree,octave,duration}` 与 `key_sections`），
合成三角波旋律 + 每拍轻点 + 4 拍预备，60 BPM。

**主音 MIDI 不写死**，而是用"内弦必须是 D4、外弦必须是 A4"这条约束从 `key_sections`
的定弦记法反推——五段互相印证通过，说明映射正确。改调式/定弦的曲子也能直接用。

`verify-render.js` 把生成的音频解回来逐音检测与 JSON 对照，
用来确认音频里真的是那些音（实测 495/495 命中，中位误差 0.08 音分）。

⚠️ 已知坑：某些简谱的八度点会有漏标。本项目《快速转调练习》的 bB 段就出现
22 个音低于二胡最低空弦 D4——用 `--bb-first6` 可只上移有问题的前 6 小节。
